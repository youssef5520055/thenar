# الفصل 04-هـ: محاكي المقبض والأجهزة (ESP32 Device Simulator)
## Chapter 04e: The Physical Hardware Simulator CLI & Flash Persistence

في مرحلة تطوير النظام وقبل تثبيت الدوائر الإلكترونية المطبوعة داخل المقبض الحديدي، كان لا بد من بناء محاكٍ فيزيائي دقيق يعمل كجهاز ESP32 افتراضي يرسل إشارات حقيقية عبر الشبكة. هذا هو دور أداة **Device Simulator** الموجودة في `apps/device-sim`.

---

### 1. لماذا بنينا أداة محاكي مستقلة (CLI Tool)؟
بدلاً من كتابة كود عشوائي داخل المتصفح، محاكي الأجهزة (`npm run sim`):
1. **يعمل كبرنامج منفصل تماماً (Independent Process):** يتصل بالـ Gateway عبر بروتوكول الشبكة الحقيقي (HTTP + WebSocket) كما لو كان جهاز ESP32 حقيقياً موضوعاً على الطاولة بجوارك.
2. **يخضع لنفس قيود الأمان:** لا يستطيع إرسال أي حركة إلا بتمرير التوكن السري (`x-device-token`).
3. **يحتوي على ذاكرة فلاش غير متطايرة (Non-Volatile Storage Emulation):** يحفظ عداد الفشل وفترة الإغلاق الأمني داخل ملف محلي (`.device-state.json`)، مما يعني أنه لو أغلقت المحاكي وأعدت تشغيله، ستظل الخزنة مغلقة أمنياً تماماً كما يحدث مع ذاكرة EEPROM/NVS لشريحة الـ ESP32 الحقيقية!

---

### 2. السيناريوهات الحركية التسعة (The 9 Simulation Scenarios)

يمكنك تشغيل أي سيناريو عبر سطر الأوامر:

```bash
# 1. فتح طبيعي للمالك الحقيقي
npm run sim -- --scenario=owner-unlock

# 2. محاولة غريبة ببصمة غير مطابقة
npm run sim -- --scenario=impostor

# 3. محاكاة تقليد مبتدئة للمقبض (Level 1 Mimicry)
npm run sim -- --scenario=mimic-l1

# 4. محاكاة تقليد متقدمة ومدروسة (Level 2 Mimicry)
npm run sim -- --scenario=mimic-l2

# 5. هجوم البصمة المسروقة بقالب السيليكون (Spoof Attack)
npm run sim -- --scenario=fingerprint-accepted-impostor

# 6. عطل مفاجئ أو فصل في سلك الحساسات (Sensor Fault)
npm run sim -- --scenario=sensor-fault

# 7. يوم عشوائي كامل يحوي خليطاً من المحاولات (Random Day)
npm run sim -- --scenario=random-day --count=5
```

---

### 3. سيناريو الهجوم الحاسم: قالب السيليكون (`fingerprint-accepted-impostor`)
هذا هو السيناريو الأهم الذي تبهر به لجنة التحكيم:
1. المهاجم صنع قالباً من الجيلاتين أو السيليكون لبصمة المالك الحقيقي.
2. الحساس البصري يفحص البصمة ويعطي: **`Gate 1: ACCEPT`** (تم اختراق الحارس الأول!).
3. لكن المهاجم يدير المقبض بيد مختلفة وقوة ضغط شاذة:
   - قوة القبضة تنحرف بأكثر من $7\sigma$ عن متوسط المالك.
   - سرعة الدوران تختلف عن العزم الطبيعي.
4. المعالج يحسب سكور التوافق فيجد: **$s(x) = -9.87$** وهو أقل بكثير من عتبة الأمان $\tau = -3.85$.
5. **النتيجة الفورية:**
   - الحارس الثاني يصد الهجوم فوراً: **`Gate 2: REJECT`**!
   - لسان السولينويد يظل ممتداً ومقفولاً بقوة السوستة الميكانيكية.
   - يزداد عداد الفشل الأمني ويتم إرسال إنذار أحمر للواجهة.

---

### 4. ما الذي سيتغير عند استبدال المحاكي بالفيرموير الحقيقي؟
عندما يتم لحام البوردة الحقيقية وربط حساسات الـ Load Cell و MPU-6050 و R503، **لن يتم تغيير أي شيء في الـ Gateway أو تطبيق الويب**!
- يتم إيقاف `apps/device-sim`.
- يتم رفع كود الـ C على شريحة الـ ESP32 الحقيقية لتقوم بنفس الاتصال بـ `ws://192.168.1.100:3000/ws/device?token=thenar-device-secret-2026`.
- كل شاشات الويب، وسجل المحاولات، والإشعارات، والرسوم البيانية ستعمل فوراً مع الهاردوير الحقيقي!
